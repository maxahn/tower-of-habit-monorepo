# Decisions — Phase 2 remainder

Resolutions where the Phase 2 tickets and the Phase 1 schema (packages/db) disagree.
The schema is treated as the source of truth for storage; tickets are implemented against
it rather than by adding tables or columns the schema's authors ruled out.

| #   | Ticket says                                                                                                                                                | Schema has                                                                                                                   | Resolution                                                                                                                                                                                                                                                                                |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P1  | Tower status `lobby` / `active`                                                                                                                            | `tower_lifecycle`: draft, active, paused, archived                                                                           | `lobby` = `draft`. A collapsed tower stays `active` with height reset. "Hibernating" is an `active` tower whose latest period outcome is `hibernated`.                                                                                                                                    |
| P2  | Membership `dormant_auto` / `dormant_voluntary`                                                                                                            | state `dormant` + `dormancy_reason` consecutive_miss / backstop / voluntary                                                  | As the 2.5 evaluator already does: auto = consecutive_miss or backstop; voluntary = voluntary.                                                                                                                                                                                            |
| P3  | `period_results` table                                                                                                                                     | `tower_periods` carries state, outcome, evaluated_at                                                                         | The period row is the result. No new table.                                                                                                                                                                                                                                               |
| P4  | `membership_events` rows                                                                                                                                   | No table                                                                                                                     | Transitions are applied to `memberships` and returned in the evaluation response. Persisting an event log is deferred (Phase 3 notifications outbox already keys dormant/returned events per membership).                                                                                 |
| P5  | Milestones, idempotent on `(tower_id, milestone_key)`                                                                                                      | No table                                                                                                                     | Out of scope for Phase 2; no schema exists. Revisit with Phase 3.                                                                                                                                                                                                                         |
| P6  | Join code: 6 chars, Crockford minus I/L/O/U                                                                                                                | `JOIN_CODE_LENGTH = 8`, alphabet without 0/O/1/I/L                                                                           | Keep 8 characters (31^8, strictly stronger than 32^6); the alphabet and length are already pinned by tests in shared and db. Rate limits per 2.18 still apply.                                                                                                                            |
| P7  | `POST /entries` body carries `localDate`; `source = live / grace`                                                                                          | `local_date` is derived server-side (DR-001); no `source` column                                                             | `localDate` is optional. When present it must be the derived tower-local date, or the previous day while that day's grace window is still open; otherwise `400 date_out_of_window`. `source` is computed in the response (grace when logged after the period's deadline), not stored.     |
| P8  | Unique violation on the one-qualifying-day index returns 200 with the existing entry; non-qualifying extras are stored                                     | §4: extra logs are stored as `counts_toward_quota = false` rows summed into the day's total                                  | An entry for an already-credited day is stored as a supplemental row (both qualifying and non-qualifying, so numeric roll-ups keep working). A genuine race on the partial index (23505) returns 200 with the existing credited row. A replayed `clientEntryId` returns the original row. |
| P9  | Numeric habits qualify on `tiers[0].threshold` (2.3)                                                                                                       | db: only `tiered` habits may have tiers                                                                                      | The db invariant is relaxed: binary habits have no tiers; numeric and tiered habits carry a ladder with tier 0. Numeric thresholds must be strictly increasing; tier indices contiguous from 0 (2.12).                                                                                    |
| P10 | 2.19: "rejects an already-evaluated period with `period_already_evaluated`" and "re-running is a no-op returning the persisted outcome"                    | —                                                                                                                            | `409 period_already_evaluated` whose `details` carries the persisted period (state, outcome, evaluated_at). Nothing is written. A period whose evaluator status is still `open`/`wobbling` is `409 period_not_due`.                                                                       |
| P11 | 2.19: claim with `SELECT … FOR UPDATE SKIP LOCKED`                                                                                                         | `claimDuePeriods` (Phase 1) claims by `evaluate_at`                                                                          | The internal endpoint locks the one named period row with `FOR UPDATE SKIP LOCKED` inside the evaluation transaction; a row held by another caller is `409 period_claimed`. The state machine still walks pending → evaluating → evaluated so the schema's claim invariants hold.         |
| P12 | 2.9/2.18: verify-code fails open on Redis outage (current code) vs. "fails closed" (2.18)                                                                  | —                                                                                                                            | 2.18 wins: `verify-code` and join-by-code fail closed (`503 rate_limiter_unavailable`); `request-code` and ordinary writes fail open.                                                                                                                                                     |
| P13 | Period windows: 2.15 says materialise via `computePeriodWindow` (policy `forward`); db's `ensureCurrentPeriod` uses `resolvePeriodWindow` (policy `later`) | —                                                                                                                            | The API materialises every period with `computePeriodWindow` (2.2) so start, preview and evaluation share one window; `ensureCurrentPeriod` stays for Phase 1 callers.                                                                                                                    |
| P14 | Habit `GET /habits/:id` "current streak"                                                                                                                   | No column                                                                                                                    | Computed from qualifying entry dates ending today or yesterday (tower-local, or user-local for a standalone habit).                                                                                                                                                                       |
| P15 | 2.6/2.21: on collapse "height is still preserved on the tower" / "height preserved at 3"                                                                   | 1.12 recompute oracle: a collapse resets `towers.height` and `current_streak` to 0; the run's height lives in its base block | The oracle wins (Phase 3 tests assert `verifyTower(...).ok`). `towers.height` is the current run; a collapsed run's height is preserved in `base_blocks.block_height` (none for a sub-minimum run). The tower's total is the sum of its blocks plus the current run.                      |
